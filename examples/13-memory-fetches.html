Memory Fetches

  1. What was missing: the cycle model in steps 1–17 counts arithmetic only. It has no term for fetching memory.
  2. The calc: replay the pixel pass and count every 64-byte block of memory it fetches (screen buffers and piece data), sorted by where the block is found: small cache (L2), big cache (L3) or RAM. A block already in the nearest cache (L1) is free. So is a block the processor's read-ahead has ready: that needs a run of consecutive blocks, and the first 8 blocks of a run are not ready. Each remaining fetch is multiplied by a price.
  3. The prices are measured on this device: one fetch from a block of memory of each size, with about 16 pixels of arithmetic between fetches, minus the same loop on a tiny block.
  4. The measurement: the step 17 pixel pass, timed twice: writing into one row that never leaves the cache (arithmetic alone), and writing into the real screen buffers. The difference is the memory cost.

Why the simple calc is too low: on short rows the read-ahead never gets ready, and fetches are too far apart in time to overlap, so a new block costs on the order of 100 cycles instead of 15–30. The calc on this page adds that rule (first 8 blocks of a run not ready). It fitted the three sizes above but has not been validated on a second mesh natively.
